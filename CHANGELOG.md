## [Unreleased] — Milestone 9: Billing & Subscription Management

Full technical reference: [docs/BILLING_ARCHITECTURE.md](docs/BILLING_ARCHITECTURE.md), [docs/STRIPE_INTEGRATION.md](docs/STRIPE_INTEGRATION.md), [docs/FEATURE_ENTITLEMENTS.md](docs/FEATURE_ENTITLEMENTS.md), decision record: [docs/adr/ADR-012-billing-and-subscriptions.md](docs/adr/ADR-012-billing-and-subscriptions.md). Scope: Stripe-backed Plans/Subscriptions/Invoices/Payments, Checkout and Customer Portal sessions, idempotent signature-verified webhook processing, and a centralized feature-entitlement gate enforced across the existing Employees/Appointments/WhatsApp modules. Analytics, marketing automation, payroll, accounting exports, CRM, and any non-Stripe payment provider remain explicitly out of scope.

### Added
- **Backend** (`modules/billing`, new): `GET /plans`; `POST/GET /subscriptions` (Checkout initiation / current state); `POST /subscriptions/{change-plan,cancel,reactivate,portal-session}` (immediate proration plan changes, cancel-at-period-end with a trial-only-immediate special case, reactivation, Stripe Customer Portal sessions); `POST /stripe/webhook` (unprefixed/unenveloped, `Stripe-Signature`-verified via the SDK's own `constructEvent`); `GET /invoices`, `GET /payments`.
- **Backend, `StripeClient`** (`infrastructure/stripe-client.ts`) — the only file importing the `stripe` SDK, mirroring `OpenAiLlmProvider`/`WhatsAppCloudApiClient`'s one-adapter precedent; every call site wraps it with a new `callStripe()` helper that maps any `StripeApiError` to a typed `503 UPSTREAM_UNAVAILABLE` (`StripeUnavailableException`) rather than leaking a raw `500` — live-verified against a real running backend with an intentionally invalid API key.
- **Backend, two-stage idempotent webhook processing** (mirroring ADR-010's WhatsApp precedent exactly): synchronous `WebhookIngestionService` (Redis `SET NX EX` fast-path + `(provider, providerEventId)` DB unique-constraint backstop, raw payload always persisted even on signature failure) hands off to an async `StripeEventProcessorService` off a new `stripe-webhook` BullMQ queue (5 attempts, exponential backoff, sharing the existing root Redis connection). Every handler (subscription/invoice/payment sync) is independently idempotent via upsert-by-Stripe-id, safe under BullMQ's at-least-once redelivery regardless of event ordering.
- **Backend, centralized entitlement gate**: `EntitlementService.assertWithinLimit(tenantId, feature, currentUsage)` — the single path any module may use to enforce a plan limit; callers compute their own usage (`EmployeeRepositoryPort.countActiveForTenant`, `AppointmentRepositoryPort.countForTenantInRange`) and pass it in, keeping the module dependency graph a one-directional DAG (`Employees`/`Appointments`/`WhatsApp` → `Billing`, no `forwardRef` needed, unlike the genuine AI↔WhatsApp cycle). `checkAndIncrementAiMessageUsage` atomically gates and meters AI/WhatsApp message quota in one call; a breach is caught specifically inside `InboundMessageProcessorService` and logged+skipped rather than crashing the queue job.
- **Backend, grace-period lifecycle sync**: a new `TenantLifecycleService.syncStatusFromBilling` maps Stripe-driven `Subscription.status` onto `Tenant.status` automatically (`TRIALING`→`TRIAL`, `ACTIVE`→`ACTIVE`, `PAST_DUE`→`PAST_DUE` — stays fully functional, not blocked — `CANCELED`→`CANCELLED`, `UNPAID`→`SUSPENDED`), independent of and additive to the existing Super-Admin-manual `suspend`/`reactivate` path.
- **Database**: new `Subscription`, `Invoice`, `Payment`, `Coupon`, `WebhookLog` models; new `SubscriptionStatus`/`InvoiceStatus`/`PaymentStatus`/`CouponDiscountType`/`CouponDurationType` enums; `Plan` gained `maxAppointmentsPerMonth`/`maxStorageMb`. Registration (`POST /auth/register`) now atomically creates a `TRIALING` `Subscription` against the cheapest active plan in the same transaction as the tenant/owner. `Subscription.stripeCustomerId` is **nullable**, populated lazily at first Checkout — a deliberate deviation from the original schema sketch, since `EntitlementService.getOrCreateForTenant` (called on nearly every tenant-scoped write path) must never require a live Stripe call just to read this row (docs/adr/ADR-012's central design decision).
- **Admin**: `GET/PATCH /admin/plans[/:id]` (plan editing, including swapping placeholder `stripePriceId`s for real ones once a live Stripe account exists), `GET /admin/tenants/:id/billing` (cross-tenant billing lookup, reached from a new "Billing" link on each `GET /admin/tenants` row).
- **Frontend**: `billing` feature — a full `/app/billing` page (current-plan card with status badge, usage bars for staff/AI-messages/appointments, a 3-tier plan comparison grid with the current plan marked, invoice and payment history tables with clean empty states); a `billingBanner` (past-due warning / trial-ending-soon notice) surfaced on the dashboard layout; the `TenantActiveGuard`'s suspended-tenant redirect target changed from a dead-end `/app/tenant-suspended` page (removed) to `/app/billing` itself, so a blocked tenant lands somewhere they can actually resolve the block. `admin` feature — `/admin/plans` (inline-editable plans table) and `/admin/tenants/:id/billing` pages.
- **Seed data**: 3 illustrative plan tiers (Starter $49/Professional $99/Business $199), each with employee/AI-message/appointment/storage limits and a placeholder `stripePriceId` — no live Stripe account exists for this project yet; swapping in real prices later is a data change via `PATCH /admin/plans/:id`, not a code change.
- **Testing**: 34 new backend unit tests (`test/unit/billing/`: entitlement, subscriptions, checkout, webhook-ingestion, event-processor services) — 349 backend unit tests total, all green. 20 new backend integration tests (`test/integration/billing/`: subscription lifecycle against a `FakeStripeClient` test double, webhook signature/idempotency, entitlement enforcement, tenant isolation) — 167 backend integration tests total (39 suites), all green, full pre-existing regression suite unmodified in behavior. 6 new frontend guard tests — 57 frontend unit tests total, all green. The whole feature additionally verified live in a real browser against a real running backend: subscription overview/usage bars/plan comparison render with real data; selecting a plan against a placeholder Stripe key correctly surfaces a clean `503` error banner (not a raw `500`) and resets UI state; admin plan-editing and tenant-billing-lookup pages render correctly with real data.
- **Documentation**: new `docs/BILLING_ARCHITECTURE.md`, `docs/STRIPE_INTEGRATION.md`, `docs/FEATURE_ENTITLEMENTS.md`, `docs/adr/ADR-012-billing-and-subscriptions.md`; `docs/API_SPECIFICATION.md` Section 13 (and new Section 16 admin-billing endpoints) amended to as-built; `docs/SYSTEM_ARCHITECTURE.md` Section 3.2, `docs/DATABASE_DESIGN.md` Section 3.8, `docs/PRISMA_SCHEMA.md` Section 10, `docs/TENANT_ARCHITECTURE.md` Section 7, and `docs/IMPLEMENTATION_ROADMAP.md` Milestone 9 amended to as-built.

### Fixed
- A concurrency race in `EntitlementService.getOrCreateForTenant`'s defensive backfill — a naive check-then-create allowed simultaneous requests for a tenant with no `Subscription` row to all race `create()`, and every loser threw an unhandled `P2002` 500 instead of finding the winner's row. Found by a pre-existing `appointments-concurrency.integration-spec.ts` test failing after this milestone's changes; fixed via a new atomic `SubscriptionRepositoryPort.upsertTrialForTenant()`, mirroring `TenantSettingsService`/`PrismaTenantSettingsRepository.createDefault`'s already-established atomic-upsert-for-backfill pattern (the same fix category Milestone 6 applied to that exact service).
- A test-fixture bug where `seedPlan()` created real, non-tenant-scoped `Plan` rows never cleaned up by `cleanupTenant()`'s cascade — silently accumulated ~70 junk plan rows in the local dev database across the session's test runs, surfaced only by live-browser verification of the plan comparison grid, not by any automated test. Fixed via a new `cleanupPlan()` fixture helper called in every billing integration test's `finally` block, plus a one-time database cleanup.

### Known Limitations
- No dunning-email flow — a failed payment relies on Stripe's own retry schedule and the grace-period `PAST_DUE` policy (stays fully functional) rather than a `Notifications`-driven failure alert; genuinely deferred (no notification-triggering mechanism existed to build on top of), not silently skipped.
- `Plan.maxStorageMb` exists on the schema but has no enforcement call site — no file-upload feature exists yet in this codebase for it to gate.
- No real Stripe account/pricing — all 3 plan tiers use placeholder `stripePriceId` values; every automated test runs against a `FakeStripeClient` or the real (unmocked) webhook-signature-verification path with a placeholder secret, never a live Stripe connection.
- `GET /admin/users`/`GET /admin/system` remain unbuilt — outside this milestone's admin scope, which was plan management and tenant billing lookup only.

## [Unreleased] — Milestone 8: AI Receptionist

Full technical reference: [docs/AI_ARCHITECTURE.md](docs/AI_ARCHITECTURE.md), [docs/PROMPT_ENGINEERING.md](docs/PROMPT_ENGINEERING.md), [docs/TOOLS.md](docs/TOOLS.md), decision record: [docs/adr/ADR-011-ai-receptionist.md](docs/adr/ADR-011-ai-receptionist.md). Scope: the AI orchestration layer — OpenAI-backed conversational booking/FAQ/escalation, orchestrating the *existing* Appointments/Availability/Services/Salon/Tenants/WhatsApp module services as tools, never duplicating their logic. Billing, analytics, marketing automation, voice, and non-WhatsApp channels remain explicitly out of scope.

### Added
- **Backend** (`modules/ai`, new): `ConversationOrchestratorService` — the tool-calling loop against OpenAI (Structured Outputs, bounded recent-message history, a fixed 7-tool set: `checkAvailability`, `bookAppointment`, `rescheduleAppointment`, `cancelAppointment`, `recommendService`, `answerFaq`, `escalateToHuman`). Real WhatsApp traffic runs it **in-process** (`InboundMessageProcessorService` calls it directly, no HTTP hop) — `POST /ai/chat` (dual-mode: internal-service credential or `MANAGER`+ JWT for the dashboard "Test my AI" sandbox) and `POST /ai/tools/{book,reschedule,cancel,faq}` (internal-service only) are a parallel, equally-real HTTP surface for QA/eval/observability, per API_SPECIFICATION.md Section 12's own design note. `GET /ai/context/:conversationId`, `GET /ai/prompt-versions` (STAFF-readable).
- **Backend, LLM provider abstraction**: `LlmProviderPort`/`OpenAiLlmProvider` — the only file importing the new `openai` package; explicit bounded retry + timeout + a single failure-exception type (`LlmProviderUnavailableException`), so swapping providers later is one new adapter class.
- **Backend, actor-abstraction for AI-initiated actions**: `AppointmentsService` gained `createAppointmentForAi`/`rescheduleAppointmentForAi`/`cancelAppointmentForAi`, `ConversationsService` gained `escalateConversation`, `MessagesService` gained `sendAiMessage` — sibling methods alongside the existing human-JWT-only ones (zero changes to any pre-existing method or call site), finally making the schema's long-reserved `ActorType.AI`/`.CUSTOMER` values actually writable, all the way down through `PrismaAppointmentRepository`'s previously-hardcoded `ActorType.USER` writes.
- **Backend, internal-service auth** (`core/guards/`, new): `InternalServiceAuthGuard` (constant-time `X-Internal-Api-Key` check, populates a synthetic `request.user` from a new `X-Tenant-Id` header so `TenantContextService`/`IdempotencyInterceptor` work unmodified) and `AiChatAuthGuard` (composes it with JWT verification for `POST /ai/chat`'s dual-mode contract) — the first non-JWT, non-webhook-signature trust boundary in this codebase.
- **Backend, human hand-off**: `ConversationStatus` gains `ESCALATED`; `Conversation` gains `escalatedAt`/`escalationReason`; a new `PATCH /conversations/:id/assign` endpoint (take over / unassign, delegating to Milestone 7's `ConversationsService.assignUser`, never exposed over HTTP until now).
- **Backend, fallback/guardrails**: an OpenAI outage resolves to the tenant's configured fallback message + auto-escalation, never a hard failure to the caller (verified live against a real running backend with an intentionally invalid API key); every tool re-validates the model's arguments against real tenant data and feeds a failure back to the model as a structured result rather than surfacing a raw error; a repeated-exact-reply counter (`AIContext.state`) substitutes for a true model-confidence score (none is exposed by the Chat Completions API) to trigger auto-escalation on a stuck clarification loop.
- **Database**: new `AIContext` (1:1 `Conversation`, Redis-cached), `ConversationSummary` (1:1 `Conversation`, a deterministic digest regenerated at escalation, not an LLM call), `PromptVersion` (an ops/debugging registry, not prompt content — actual prompts are versioned files under `modules/ai/prompts/`, self-registered on boot) models; `Message.aiPromptVersion`, `Conversation.escalatedAt`/`.escalationReason` columns. AI behavior config (`general.ai.*`: enabled/tone/greeting/escalation-instructions/fallback-message/confidence-threshold) needed **no** schema migration — it lives inside `TenantSettings`'s existing `general` JSON namespace, per that model's own documented design.
- **RBAC**: new `ai:manage` permission, granted to `OWNER`/`MANAGER` (mirrored on the frontend's `role-permissions.constant.ts`).
- **Frontend**: Settings page gained an "AI Behavior" section (typed form, live WhatsApp-bubble greeting preview, a read-only Prompt Versions table, and a "Test my AI" sandbox); the Conversations inbox gained a status-filter chip row (All/Escalated/Open/Resolved/Closed), AI-vs-staff message-bubble badges, "Take over"/"Unassign" actions on escalated conversations, and a dev-only (`!environment.production`) AI reasoning/debug panel.
- **Infrastructure fix**: `tsconfig.build.json` gained `rootDir: "./src"` (and excludes `prisma/`) — fixes a pre-existing, unrelated bug where `nest build`'s output landed at `dist/src/...` while `package.json`'s `start:prod` (`node dist/main`) expected `dist/...` directly; surfaced by this milestone's need for `nest-cli.json`'s new static-asset copying (the versioned prompt `.md` files) to resolve correctly at runtime.
- **Testing**: extensive new backend unit coverage (`test/unit/ai/*`, plus new cases in `test/unit/appointments/appointments.service.spec.ts`, `test/unit/whatsapp/{conversations,messages}.service.spec.ts`, `test/unit/core/{internal-service-auth,ai-chat-auth}.guard.spec.ts`) — 315 backend unit tests total, all green. New integration suites (`test/integration/ai/{ai-chat,tenant-isolation,human-handoff}.integration-spec.ts`, a scripted `LlmProviderPort` test double so no real OpenAI spend is needed) covering the full chat flow, tool guardrails, tenant isolation, and the complete human-handoff lifecycle — 147 backend integration tests total, all green, full pre-existing regression suite unmodified in behavior. 51 frontend unit tests, all green. The whole feature additionally verified live in a real browser against a real running backend (login → Settings AI Behavior renders → Prompt Versions table reflects real self-registered DB rows → "Test my AI" round-trips through the real orchestrator and correctly renders the fallback/degraded path).
- **Documentation**: new `docs/AI_ARCHITECTURE.md`, `docs/PROMPT_ENGINEERING.md`, `docs/TOOLS.md`, `docs/adr/ADR-011-ai-receptionist.md`; `docs/API_SPECIFICATION.md` Section 12 (and the new `PATCH /conversations/:id/assign` in Section 11), `docs/SYSTEM_ARCHITECTURE.md` Section 5, `docs/DATABASE_DESIGN.md` Sections 3.6.3/3.6.4/10.2, `docs/PRISMA_SCHEMA.md` Section 8, `docs/FRONTEND_ARCHITECTURE.md` Sections 6.6/6.9, `docs/MESSAGING_ARCHITECTURE.md`, and `docs/IMPLEMENTATION_ROADMAP.md` amended to as-built.

### Known Limitations
- No streaming — no SSE/WebSocket transport exists anywhere in this codebase to build it on; `LlmProviderPort` is shaped to not preclude adding it later.
- No plan-based AI usage limiting (`403 PLAN_MESSAGE_LIMIT_EXCEEDED`) — depends on `Subscription`, which doesn't exist until Milestone 9 (Billing).
- No true model-confidence-based escalation — see the repeated-exact-reply proxy above.
- `POST /ai/chat`'s `customerPhoneNumber`-based conversation resolution isn't built — `channel: "whatsapp"` requires an already-resolved `conversationId`, matching the in-process production path's own precondition (real customer traffic never calls this endpoint at all).
- Voice, SMS, or any non-WhatsApp channel remain out of scope.

## [Unreleased] — Milestone 7: WhatsApp Cloud Platform Integration

Full technical reference: [docs/WHATSAPP_ARCHITECTURE.md](docs/WHATSAPP_ARCHITECTURE.md), [docs/MESSAGING_ARCHITECTURE.md](docs/MESSAGING_ARCHITECTURE.md), decision record: [docs/adr/ADR-010-whatsapp-platform.md](docs/adr/ADR-010-whatsapp-platform.md). Scope: WhatsApp Business Cloud API connection, signature-verified webhook ingestion, `Conversation`/`Message` persistence with two-layer idempotency, contact synchronization, manual outbound replies, and a two-pane frontend inbox. AI receptionist, billing, analytics, and marketing automation remain explicitly out of scope.

### Added
- **Backend** (`modules/whatsapp`, new — a single module, not the three separate `Conversations`/`Messages`/`WhatsApp` modules originally sketched, layered per aggregate internally): `GET/POST/DELETE /whatsapp/account` (connect/disconnect, credential-verified against Meta before persisting, `whatsapp:manage` permission); `GET/POST /webhooks/whatsapp` (Meta's verification handshake + signature-verified inbound event receiver, unprefixed/unenveloped like `/health`); `GET/PATCH /conversations[/:id]`; `GET /messages`, `POST /messages/send` (`202 Accepted`, `Idempotency-Key` required, `422 OUTSIDE_MESSAGING_WINDOW` past 24h since the customer's last inbound message).
- **Backend, first BullMQ integration**: two named queues, `whatsapp-inbound` (parses webhook events into `Conversation`/`Message` rows) and `whatsapp-outbound` (sends queued messages via the Cloud API), each with 5-attempt exponential backoff and terminal (non-retried) handling for permanent 4xx failures — `src/queues/` was previously an empty, reserved placeholder; `queues/bullmq-root.module.ts` is the first job-queue consumer in this codebase.
- **Backend, first decryptable stored secret**: `core/security/encryption.service.ts` (AES-256-GCM) encrypts `WhatsAppAccount.accessTokenEncrypted` at rest, decrypted only immediately before an outbound Cloud API call — every other stored secret in this codebase is one-way hashed.
- **Backend, two-layer inbound idempotency** (mirroring ADR-009's booking-conflict precedent): a Redis dedup check (`dedup:whatsapp:{whatsappMessageId}`) ahead of a partial-unique index on `messages.whatsappMessageId` (manual migration) — verified with a webhook-replay integration test (the identical signed payload delivered twice produces exactly one `Message` row).
- **Backend, contact synchronization**: a new `CustomerService.findOrCreateByPhoneForTenant` method (Milestone 6's `Customers` module) — an inbound message from an unknown phone number creates a `Customer` automatically, using the WhatsApp profile display name as a one-time `firstName` fallback.
- **Database**: new `WhatsAppAccount`, `Conversation`, `Message`, `WebhookEvent` models; new `WhatsAppConnectionStatus`/`ConversationStatus`/`MessageDirection`/`MessageType`/`MessageDeliveryStatus`/`WebhookProcessingStatus` enums (`Message.senderType` reuses the existing `ActorType` enum rather than a new one). `Tenant`/`Customer`/`User` gained additive back-relations.
- **RBAC**: new `whatsapp:manage` permission key, granted to `OWNER`/`MANAGER` — gates only WhatsApp account connect/disconnect; conversation/message read and reply are `STAFF`-broad, matching the `appointments:manage`/`customers:manage` precedent of gating only the most sensitive action per resource.
- **Frontend**: `conversations` feature — `ConversationsInboxPage` (`/app/conversations[/:id]`, a two-pane inbox: conversation list, message thread with a 24-hour-window-aware composer, contact panel with status controls), `ConversationsApiService`; a new "WhatsApp" section on the existing Settings page (connect form, connection status, disconnect); "Conversations" nav link.
- **Testing**: 71 new backend unit tests (webhook signature verification, encryption round-trip, `WhatsAppAccountService`, `ConversationsService`, `MessagesService` including the 24h-window boundary, `InboundMessageProcessorService` including duplicate/replay/cold-Redis-race scenarios, `OutboundMessageService` including transient-vs-permanent retry classification) plus 4 new `CustomerService` tests for contact sync; 19 new backend integration tests (`test/integration/whatsapp/`) covering webhook signature validation, webhook replay/duplicate handling, unknown-`phone_number_id` handling, conversation/message CRUD, cross-tenant isolation, `whatsapp:manage` RBAC, and a live (real Meta API call with intentionally-invalid test credentials) credential-rejection path — full existing regression suite (260 unit + 137 integration tests total) verified green. Frontend feature verified end-to-end in a real browser: login → Settings WhatsApp section renders → a real signature-verified webhook POST processed end-to-end through the actual BullMQ worker → the resulting conversation/message appear live in the inbox → a staff reply sent through the composer.
- **Documentation**: new `docs/WHATSAPP_ARCHITECTURE.md`, `docs/MESSAGING_ARCHITECTURE.md`, `docs/adr/ADR-010-whatsapp-platform.md`; `docs/API_SPECIFICATION.md` Section 11, `docs/DATABASE_DESIGN.md` Section 3.6/3.7, and `docs/PRISMA_SCHEMA.md` Section 8 amended to as-built; `docs/IMPLEMENTATION_ROADMAP.md` Milestone 7 execution note.

### Known Limitations
- No `TemplateMessage` registry — outbound replies past the 24-hour customer-service window are rejected (`422 OUTSIDE_MESSAGING_WINDOW`), not template-routed. Genuinely deferred, not silently skipped (see the ADR).
- No media file download/S3 storage — only metadata (Meta's media id/mime-type/sha256/filename/size, all present in the webhook payload already) is persisted; the `Files`/S3 module itself remains an open gap carried forward from Milestone 5.
- No AI auto-response or conversation escalation states — `ConversationStatus` is `OPEN`/`RESOLVED`/`CLOSED` only; Milestone 8's territory entirely.
- No live delivery-status polling in the frontend — `Message.status` updates server-side as Meta's delivery receipts arrive, but the UI doesn't currently poll/subscribe for live updates after sending; a page refresh reflects the latest state.
- Live inbound webhook delivery requires a public HTTPS callback URL registered in Meta's App Dashboard — an operational step outside this codebase, tracked the same way Sprint 1.1's WhatsApp Business verification already was.

## [Unreleased] — Milestone 6: Appointment & Scheduling Engine

Full technical reference: [docs/SCHEDULING_ARCHITECTURE.md](docs/SCHEDULING_ARCHITECTURE.md), [docs/CALENDAR_ENGINE.md](docs/CALENDAR_ENGINE.md), decision record: [docs/adr/ADR-009-scheduling-engine.md](docs/adr/ADR-009-scheduling-engine.md). Scope: Customer CRUD (deferred out of Milestone 5, picked up now since Appointments needs it), the Availability slot-computation engine, and the full Appointment booking lifecycle (create, cancel, reschedule, list, get) with two-layer conflict prevention. WhatsApp, AI, Billing, Analytics, and notifications beyond scheduling remain out of scope.

### Added
- **Backend** (`Customers` module, new): `GET/POST/PATCH/DELETE /customers[/:id]` — cursor-paginated list, `q` search, `409 PHONE_NUMBER_ALREADY_EXISTS` on duplicate phone within a tenant.
- **Backend** (`Availability` module, new, no controller of its own): slot computation against `WorkingHours`/`EmployeeTimeOff`/`Holiday`/`BusinessHours`/existing bookings and the buffer-composition rule (`max(service.bufferTimeMinutes, TenantSettings.business.bookingBufferMinutes)` — the first real read of the dormant `business` namespace); served via `GET /appointments/availability`.
- **Backend** (`Appointments` module, new): `GET/POST/PATCH/DELETE /appointments[/:id]`, `POST /appointments/:id/cancel`, `POST /appointments/:id/reschedule` — **confirmed-with-requester per-service employee assignment**: a single visit's services may each be performed by a different employee, so `POST /appointments`'/`.../reschedule`'s request bodies take a `services: [{ serviceId, employeeId }]` array rather than one appointment-level `employeeId`. STAFF scoped to their own linked employee's appointments (403, not 404).
- **Backend, two-layer booking-conflict prevention** (DATABASE_DESIGN.md Risk DB-R3, closed as designed): a Redis distributed lock (`core/locking/booking-lock.service.ts`, `SET NX PX` per distinct employee, sorted-order acquisition) plus a `btree_gist EXCLUDE` constraint on `appointment_services` (manual migration SQL) as the database-level backstop — verified with a scripted concurrency integration test (8 concurrent requests for the same slot, exactly one succeeds).
- **Backend, reusable primitives**: a generic `Idempotency-Key` interceptor (`core/idempotency/`, Redis-backed, 24h TTL, required on appointment create/cancel/reschedule) and a generic cursor-pagination utility (`common/utils/cursor-pagination.util.ts`) — both pulled forward from later in the roadmap since this milestone's own endpoints are their natural first consumers, and both reusable by any future module.
- **Database**: new `Customer`, `Appointment`, `AppointmentService`, `AppointmentStatusHistory` models; new `AppointmentStatus`/`AppointmentHistoryAction` enums. `AppointmentService` carries per-line `startTime`/`endTime`/`blockedUntil`/`isBlocking` — the per-service-employee-assignment decision makes each line, not the parent appointment, the independently-blocking conflict-prevention unit.
- **RBAC**: two new permission keys, `customers:manage` and `appointments:manage`, granted to `OWNER`/`MANAGER` — gating only each resource's most sensitive action (`DELETE`), not every write, since `POST`/`PATCH`/cancel/reschedule are open to `STAFF` per the API spec's own authorization rows.
- **Frontend**: `customers` feature — `CustomersListPage` (`/app/customers`, search + inline create/edit); `appointments` feature — `AppointmentsCalendarPage` (`/app/appointments`, Day/Week views, one column per calendar day with native HTML5 drag-and-drop rescheduling between days), `AppointmentFormPage` (`/app/appointments/new`, multi-service line builder with per-line employee eligibility, availability-slot suggestions), `AppointmentDetailPage` (`/app/appointments/:id`, cancel/reschedule/remove); `CustomersApiService`/`AppointmentsApiService`; "Customers"/"Appointments" nav links. `ApiClient` gained a `headers` option (its first consumer: attaching `Idempotency-Key`).
- **Testing**: 45 new backend unit tests (`CustomerService`, `AvailabilityService`, `AppointmentsService`, `BookingLockService`, cursor-pagination util); 25 new backend integration tests (`test/integration/customers/`, `test/integration/appointments/`, including a dedicated concurrency race spec) covering CRUD, cursor pagination, cross-tenant isolation, RBAC/STAFF-scoping, and the two-layer conflict-prevention mechanism against a real database and Redis — full existing regression suite (203 unit + 118 integration tests total) verified green. Frontend feature verified end-to-end in a real browser (login → create customer → book appointment → calendar display → cancel).
- **Documentation**: new `docs/SCHEDULING_ARCHITECTURE.md`, `docs/CALENDAR_ENGINE.md`, `docs/adr/ADR-009-scheduling-engine.md`; `docs/API_SPECIFICATION.md` Sections 9/10 updated to as-built (per-service employee assignment amendment, real cursor pagination/`Idempotency-Key`); `docs/DATABASE_DESIGN.md`/`docs/PRISMA_SCHEMA.md` amended (`customers`/`appointments`/`appointment_services`/`appointment_status_history` as-built notes); `docs/IMPLEMENTATION_ROADMAP.md` Milestone 6 execution note.

### Fixed
- A genuine, pre-existing race condition in `TenantSettingsService.getSettings()`'s `createDefault` fallback (Milestone 3) — `upsert()` alone was not concurrency-safe (two simultaneous callers could both miss the row on read and both attempt insert, the second raising an unhandled `P2002`). Found by this milestone's own concurrency test (the first caller to invoke `getSettings` under genuine concurrent load); fixed in `PrismaTenantSettingsRepository.createDefault` by catching the conflict and re-reading rather than crashing.

### Known Limitations
