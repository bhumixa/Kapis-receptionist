# ADR-012: Billing & Subscription Management (Milestone 9)

**Status:** Accepted
**Date:** 2026-07-25
**Milestone:** 9 — Billing & Subscription Management
**Related:** docs/BILLING_ARCHITECTURE.md, docs/STRIPE_INTEGRATION.md, docs/FEATURE_ENTITLEMENTS.md, docs/DATABASE_DESIGN.md §3.8, docs/PRISMA_SCHEMA.md §10, docs/API_SPECIFICATION.md §13, docs/SYSTEM_ARCHITECTURE.md §3.2, docs/TENANT_ARCHITECTURE.md, docs/adr/ADR-006-multi-tenant-saas-engine.md, docs/adr/ADR-010-whatsapp-platform.md

---

## Decision

Build a single `modules/billing` module (Clean Architecture: `domain/{entities,ports}`, `application/*.service.ts`, `infrastructure/*`, `interface/*`, `queues/*`) that is the sole owner of `Plan`, `Subscription`, `Invoice`, `Payment`, `Coupon`, and `WebhookLog`. Every other module that needs to enforce a plan limit (`Employees`, `Appointments`, `WhatsApp`) depends on `BillingModule` one-directionally, calling a single exported gate — `EntitlementService.assertWithinLimit(tenantId, feature, currentUsage)` — never reading `Plan`/`Subscription` fields directly. Stripe is reached exclusively through `StripeClient` (`infrastructure/stripe-client.ts`), the only file importing the `stripe` SDK, mirroring `OpenAiLlmProvider`'s and `WhatsAppCloudApiClient`'s existing single-adapter precedent. Webhook processing follows the same synchronous-ingest/asynchronous-process split with two-layer idempotency (Redis + DB unique constraint) already established by `docs/WHATSAPP_ARCHITECTURE.md` §4.

## Context

Every module this milestone needed to integrate with already existed: `Tenant.status` and `TenantLifecycleService` (Milestone 3, ADR-006), `Employees`/`Appointments` (Milestones 4-6), and the WhatsApp inbound pipeline that triggers AI responses (Milestones 7-8, ADR-010/ADR-011). Two of those milestones' own ADRs explicitly deferred billing: ADR-010 left `ConversationStatus` AI-shaped but didn't touch usage limits, and ADR-011 explicitly noted "No plan-based usage limiting... depends on `Subscription`, which doesn't exist until Milestone 9." This ADR is that dependency landing.

The central technical tension: `Subscription` needs a `stripeCustomerId` to be a real, usable Stripe integration — but nearly every tenant-scoped write path in the app (any Employee/Appointment create, and indirectly every AI-triggered WhatsApp reply) now runs through `EntitlementService.getOrCreateForTenant`, which must never require a live network call to Stripe just to check a number against a limit. Resolving this without weakening the Stripe integration itself is this ADR's central design decision.

## Key Design Decisions

| Decision | Summary | Rationale |
|---|---|---|
| `Subscription.stripeCustomerId` is nullable, populated lazily | Registration (`PrismaRegistrationRepository`) creates a `TRIALING` `Subscription` against the cheapest active `Plan` in the same transaction as the tenant/owner — with `stripeCustomerId: null`. The Stripe Customer itself is created exactly once, lazily, inside `CheckoutService.createCheckoutSession`, the first time a tenant actually starts a paid Checkout. Every other entitlement path (`EntitlementService.getOrCreateForTenant`, called on nearly every tenant-scoped write) is a pure DB read/upsert — zero Stripe network calls. | The alternative — a required `stripeCustomerId`, matching the original design docs — would force a live Stripe API call during registration and during the entitlement backfill that now runs on almost every write path across Employees/Appointments/WhatsApp, a severe reliability and testability regression (and a hard block for the ~all pre-existing integration tests that use `seedOwner()`, which bypasses registration entirely). Deviates from `DATABASE_DESIGN.md`'s original schema sketch — documented there directly (§3.8, "Amended, Milestone 9") rather than silently. |
| `EntitlementService.assertWithinLimit` takes usage as a parameter, never queries it | `BillingModule` exports one gate; `EmployeeService`, `AppointmentsService`, and `InboundMessageProcessorService` each compute their own current usage from their own repository (`countActiveForTenant`, `countForTenantInRange`) and pass it in. `EntitlementService` never imports `EmployeeRepositoryPort`/`AppointmentRepositoryPort`. | Keeps the module dependency graph a strict DAG (`Employees/Appointments/WhatsApp → Billing`, never the reverse) — no `forwardRef()` needed, unlike the genuine AI↔WhatsApp cycle (ADR-011), because billing never needs to *read* another module's data, only a number the caller already has cheaply. See docs/FEATURE_ENTITLEMENTS.md §2.1 for the full argument. |
| Atomic `upsertTrialForTenant`, not check-then-create | `SubscriptionRepositoryPort` gained `upsertTrialForTenant`, backed by a Prisma `upsert` (`update: {}` no-op on conflict) plus a `P2002` catch-and-refetch as defense-in-depth. `EntitlementService.getOrCreateForTenant` calls this instead of a naive `findByTenantId` → `create`. | Discovered via a pre-existing concurrency integration test (`appointments-concurrency.integration-spec.ts`) failing after this milestone's changes: concurrent requests for a tenant with no `Subscription` row all raced to `create()`, and every loser threw an unhandled `P2002` 500 instead of finding the winner's row. Mirrors `TenantSettingsService`/`PrismaTenantSettingsRepository.createDefault`'s already-established atomic-upsert-for-defensive-backfill pattern exactly — not a new idiom, a reapplication of one. |
| Grace-period policy: `PAST_DUE` stays fully functional | Only `CANCELED`/`UNPAID` (Stripe's own dunning retries exhausted) map to a blocking `Tenant.status` (`CANCELLED`/`SUSPENDED`). `PAST_DUE` maps to `Tenant.status: PAST_DUE`, which `TenantActiveGuard` does not block — a tenant whose card was declined once keeps full product access while Stripe's own retry schedule runs. `INCOMPLETE` (initial payment still processing) has no `Tenant.status` mapping at all — left unchanged until Stripe resolves it one way or the other. | Approved by the user (AskUserQuestion, "Grace period (Recommended)") over an immediate-suspend-on-first-failure alternative. Matches common SaaS practice: a single failed charge is rarely a deliberate cancellation, and hard-blocking product access on it would be a harsh, support-ticket-generating default for a milestone with no dunning-email system built yet. |
| Immediate plan change with proration, one code path for upgrade and downgrade | `SubscriptionsService.changePlan` calls `StripeClient.changeSubscriptionPrice` synchronously (if a live Stripe subscription exists) and updates the local `Subscription.planId` in the same request — no scheduled/deferred change, no separate downgrade flow. | Approved by the user (AskUserQuestion, "Immediate with proration (Recommended)") over deferred-to-period-end. Stripe's own proration billing handles the fairness concern natively; a single code path avoids a second state machine (`pendingPlanId`/`effectiveAt`) for a milestone explicitly scoped to placeholder plan tiers, not real pricing-strategy nuance. |
| Three illustrative plan tiers, placeholder `stripePriceId` values | `prisma/seed.ts` seeds Starter/Professional/Business ($49/$99/$199) with limits on employees, AI messages, appointments/month, and storage; each `stripePriceId` is a placeholder string (`price_placeholder_*`), not a real Stripe Price. | Approved by the user (AskUserQuestion, "3 illustrative tiers with placeholders (Recommended)"). No real Stripe account exists for this project yet; real pricing is a product decision outside this milestone's scope. Swapping in real `stripePriceId`s later is a data change (`PATCH /admin/plans/:id`), not a code change — see docs/STRIPE_INTEGRATION.md §6. |
| Mocked Stripe for all automated tests; real SDK, placeholder keys, for local dev | Unit tests never touch `StripeClient`. Integration tests swap it for `FakeStripeClient` via `createTestApp`'s new `overrideProviders` hook (mirroring AI's `ScriptedLlmProvider` precedent). Webhook signature tests sign payloads with the same placeholder `STRIPE_WEBHOOK_SECRET` the app is configured with, exercising the *real*, unmocked `StripeClient.constructWebhookEvent` fully offline (Stripe's HMAC scheme is symmetric, so this needs no live Stripe connection). | Approved by the user (AskUserQuestion, "Build with mocks now (Recommended)"). No Stripe account/API keys exist yet; blocking the milestone on obtaining them would stall all of Checkout/Portal/webhook development. `callStripe()`'s error-mapping (`StripeApiError` → `503 UPSTREAM_UNAVAILABLE`) was live-verified against a real running backend with an intentionally invalid key, confirming the failure path independent of having real credentials. |
| Two-layer webhook idempotency, reused verbatim from WhatsApp | `WebhookIngestionService`: Redis `SET NX EX` on `dedup:stripe:{event.id}` (fast path) + `WebhookLog`'s `@@unique([provider, providerEventId])` (DB backstop) + always-persist-even-on-signature-failure for forensic visibility. Async processing (`StripeEventProcessorService`, off a new `stripe-webhook` BullMQ queue, sharing the root Redis connection) upserts `Invoice`/`Payment` by their Stripe ids and resolves tenant via `stripeCustomerId` — never via `TenantContextService`, the documented exception a webhook (no JWT) always needs. | Stripe, like Meta's WhatsApp webhooks, retries on any non-2xx/timeout and offers no built-in exactly-once guarantee. Rather than design a new idempotency mechanism, this milestone reused `docs/WHATSAPP_ARCHITECTURE.md` §4's exact shape — a second validated instance of the same pattern, not a new one to independently review. |
| Every billing state transition writes an `AuditLog` row | Plan changes, cancellations, reactivations, and Stripe-driven syncs (`SUBSCRIPTION_SYNCED_FROM_STRIPE`) all call `AuditLogService.record`, with `actorType: SYSTEM`/`actorId: null` for webhook-driven changes and `actorType: USER` for owner-initiated ones. | Explicit milestone requirement ("every billing change generates an AuditLog"). Reuses the existing `AuditLogService`/actor-reference pattern (`ActorType` enum) established since Milestone 3 — no new audit mechanism. |
| No new payment provider, no Analytics/Marketing/Payroll/Accounting/CRM scope | Not built. | Explicitly excluded by this milestone's brief. |

## Consequences

- `BillingModule` is imported by `EmployeesModule`, `AppointmentsModule`, and `WhatsAppModule` — three new one-directional edges into the module dependency graph, none of them circular.
- `stripe` is now a standing dependency, reached through exactly one file (`StripeClient`), consistent with this codebase's established one-adapter-per-third-party convention (`OpenAiLlmProvider`, `WhatsAppCloudApiClient`).
- `bullmq-root.module.ts`'s shared Redis connection gained a second consumer queue (`stripe-webhook`) — no second Redis connection was needed, mirroring `whatsapp-inbound`'s existing setup.
- `AuthModule`'s registration transaction is measurably larger (now also creates a `Subscription` row) but every pre-existing registration test and call site is unchanged in observable behavior — confirmed by the full pre-existing auth test suite passing unmodified.
- `TenantLifecycleService` gained `syncStatusFromBilling`, the one path Stripe-driven state is allowed to write `Tenant.status` through — kept distinct from the admin-initiated `updateStatus` path so the two audit trails (billing-driven vs. admin-driven suspension) stay distinguishable.
- Discovered and fixed during this milestone, unrelated to the schema/architecture decisions above: a test-fixture bug (`seedPlan()` creating real, non-tenant-scoped `Plan` rows never cleaned up by `cleanupTenant()`'s cascade) had silently accumulated ~70 junk `Plan` rows in the local dev database across the session's test runs, surfaced only by live-browser verification of the plan comparison grid, not by any automated test. Fixed via a `cleanupPlan()` fixture helper now called in every billing integration test's `finally` block, plus a one-time DB cleanup. Documented here as a caution: fixtures that create *global* (non-tenant-scoped) rows need their own explicit cleanup obligation — `cleanupTenant()`'s cascade cannot catch them.
- Live-verified in a real browser against a real running backend: subscription overview, usage bars, and the 3-tier plan comparison grid render correctly with real data; selecting a different plan against a placeholder Stripe key correctly surfaces a clean `503`-mapped error banner (not a raw `500`) and resets UI loading state; admin plan-editing and tenant-billing-lookup pages render correctly.
