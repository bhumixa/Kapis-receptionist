# ADR-011: AI Receptionist (Milestone 8)

**Status:** Accepted
**Date:** 2026-07-24
**Milestone:** 8 — AI Receptionist
**Related:** docs/AI_ARCHITECTURE.md, docs/PROMPT_ENGINEERING.md, docs/TOOLS.md, docs/DATABASE_DESIGN.md §3.6.3-3.6.4/§10.2, docs/PRISMA_SCHEMA.md §8, docs/API_SPECIFICATION.md §12, docs/SYSTEM_ARCHITECTURE.md §5, docs/adr/ADR-009-scheduling-engine.md, docs/adr/ADR-010-whatsapp-platform.md, docs/IMPLEMENTATION_ROADMAP.md

---

## Decision

Build a single `modules/ai` module (Clean Architecture: `domain/{entities,ports}`, `application/*.service.ts`, `infrastructure/*`, `interface/*`) that orchestrates the *existing* `Appointments`/`Availability`/`Services`/`Salon`/`Tenants`/`WhatsApp` module services as tools — never a parallel or duplicated implementation of booking, availability, or messaging logic. The module's `ConversationOrchestratorService` is the single entry point for a conversational turn; `WhatsAppModule`'s `InboundMessageProcessorService` calls it **in-process** (a normal injected NestJS provider call, no HTTP hop) for every real customer message, matching SYSTEM_ARCHITECTURE.md §5.3's original design intent. `POST /ai/chat` and `POST /ai/tools/*` exist as a parallel, equally-real HTTP surface for the dashboard "Test my AI" sandbox and for QA/eval/future-extraction — per API_SPECIFICATION.md §12's own architectural note — not because production traffic uses them.

OpenAI is reached exclusively through a provider abstraction (`LlmProviderPort`/`OpenAiLlmProvider`) so a future provider swap is one new adapter class, never a change to the orchestrator or tool layer.

## Context

Every module this milestone needed already existed: the booking engine (Milestone 6) with its two-layer conflict-prevention mechanism, the WhatsApp transport and `Conversation`/`Message` persistence (Milestone 7, ADR-010), and RBAC/tenant-context infrastructure (Milestones 2-3). ADR-010 deliberately left `ConversationStatus`/`Message.senderType` AI-shaped-but-unused ("Milestone 8's job") — this ADR is that job.

The one genuine technical obstacle: every mutating method on `AppointmentsService`/`ConversationsService`/`MessagesService` was written exclusively against a real JWT-authenticated human (`AccessTokenPayload`), with `ActorType.USER` hardcoded into every audit/history write — right down into the Prisma repository layer. `ActorType.AI`/`.CUSTOMER` already existed in the schema (reserved since Milestone 7) but were never actually usable. Resolving this cleanly, without duplicating the booking/messaging logic those services already had correctly and were tested against, is this ADR's central design decision.

## Key Design Decisions

| Decision | Summary | Rationale |
|---|---|---|
| Actor-abstraction: sibling `*ForAi` methods, not a signature rewrite | `AppointmentsService` gained `createAppointmentForAi`/`rescheduleAppointmentForAi`/`cancelAppointmentForAi`; `ConversationsService` gained `escalateConversation`; `MessagesService` gained `sendAiMessage`. Every existing public method and HTTP call site is untouched. The shared private internals (`buildLines`, `withEmployeeLocks`, `createWithConflictHandling`) already took primitives, not `AccessTokenPayload` — only the STAFF-ownership-scoping check did, and that's exactly what AI calls skip (an AI/customer-initiated action always acts at full-tenant scope, the same reach as OWNER/MANAGER). `AppointmentRepositoryPort`'s `CreateAppointmentInput`/`cancel` input gained `actorType: ActorType`/`actorId: string \| null` (widened from an always-`ActorType.USER`, always-non-null shape), threaded down to the four previously-hardcoded `actorType: ActorType.USER` writes in `PrismaAppointmentRepository`. | The alternative — rewriting the existing public methods to accept a union of `AccessTokenPayload \| AiActorContext` — would touch every call site of "the highest-stakes service in the codebase" (its own doc comment's words) for a change that's actually orthogonal to any existing behavior. Zero regression risk to Milestone 6's booking-conflict-prevention test suite, confirmed by that suite passing unmodified. |
| Real traffic is in-process; `/ai/tools/*`/`/ai/chat` are a parallel HTTP surface | `InboundMessageProcessorService` injects `ConversationOrchestratorService` directly (resolved via `forwardRef` between `AiModule`/`WhatsAppModule` — a genuine circular module dependency, the same `forwardRef`-on-both-sides pattern `CoreModule`/`AuthModule`/`TenantsModule` already established). `AiChatController`/`AiToolsController` call the exact same application services. | SYSTEM_ARCHITECTURE.md §5.3 designs tool execution as in-process calls; API_SPECIFICATION.md §12 exposes real HTTP endpoints anyway for testability/observability/future-extraction. Both are true simultaneously because they're the same underlying implementation reached two ways — no duplication either way. |
| Internal-service-credential auth, built from scratch | New `InternalServiceAuthGuard` (`core/guards/`): validates a shared-secret `X-Internal-Api-Key` header (constant-time compare, `AI_INTERNAL_API_KEY`) and — critically — **populates `request.user`** with a synthetic, role-less `AccessTokenPayload` (`tenantId` read from a new `X-Tenant-Id` header, mirroring the existing `X-Impersonate-Tenant-Id` header-based-context precedent). `AiChatAuthGuard` composes it with standard JWT verification for `POST /ai/chat`'s dual-mode contract (internal service OR `MANAGER`+ JWT for `channel: "dashboard_test"`). | No non-JWT trust boundary existed before this milestone except WhatsApp's webhook HMAC-signature check (single-purpose, not reusable — there's no third party signing these requests). Populating `request.user` is the detail that makes `TenantContextService`/`IdempotencyInterceptor` (required on the three mutating tool endpoints) work completely unmodified for an internal-service caller. |
| `ConversationStatus` gains one value: `ESCALATED` — no `HUMAN_HANDLING` | The pre-Milestone-7 design (PRISMA_SCHEMA.md, DATABASE_DESIGN.md) specified `OPEN_AI`/`ESCALATED`/`HUMAN_HANDLING`/`RESOLVED`/`CLOSED`. As-built: `OPEN`/`ESCALATED`/`RESOLVED`/`CLOSED`. The already-existing `Conversation.assignedUserId` distinguishes "queued, unclaimed" (`ESCALATED` + `assignedUserId IS NULL`) from "claimed by staff" (`ESCALATED` + `assignedUserId` set) — the same signal a second enum value would encode. `OPEN_AI` doesn't reappear either: Milestone 7 already ships every conversation as `OPEN` by default, and gating AI auto-response is a tenant-setting concern (`general.ai.enabled`), not a per-conversation status. | Matches this codebase's own repeated "narrow the ask, log the deferral" precedent (ADR-009, ADR-010). `Conversation` gained `escalatedAt`/`escalationReason` (additive columns); a new `escalate()` repository method sets all three atomically. `docs/FRONTEND_ARCHITECTURE.md`/`docs/API_SPECIFICATION.md`'s original two-state filter language is superseded by this ADR — see those docs' updated Milestone 8 notes. |
| `TenantSettings` schema: **no migration** | AI behavior config (greeting, tone, escalation instructions, enabled toggle, fallback message, repeated-clarification threshold) lives inside the existing `general` JSON namespace as a nested `ai` object (`general.ai.*`), read/written through the existing `TenantSettingsService`. | `TenantSettings`'s own doc comment already establishes this: "adding a field to a namespace is an application-layer change, never a schema migration" — the exact scenario this milestone needed. `PATCH /tenant/settings`'s existing shallow-merge-per-namespace behavior (`prisma-tenant-settings.repository.ts`) means the Settings page's raw-JSON "General" textarea and the new typed "AI Behavior" form can edit the same `general` object without a race: an incoming `general` PATCH that omits the `ai` key never overwrites it, by construction. |
| Three new models: `AIContext`, `ConversationSummary`, `PromptVersion` | `AIContext` (1:1 `Conversation`, `currentIntent`/`state` JSONB/`lastToolCall`) — durable working memory, Redis-cached (`ai:context:{conversationId}`, a few hours TTL) in front of it. `ConversationSummary` (1:1 `Conversation`) — a deterministic digest (not an LLM call) regenerated at natural checkpoints (escalation), never on every message. `PromptVersion` — an **ops/debugging registry only** (which version of a named prompt is active), decoupled by plain version-string columns (`Message.aiPromptVersion`, `ConversationSummary.aiPromptVersion`) rather than a foreign key — actual prompt *content* lives in versioned files under `modules/ai/prompts/`, self-registered into this table on `PromptBuilderService.onModuleInit()`. | Matches PRISMA_SCHEMA.md/DATABASE_DESIGN.md's original design intent for the first two; `PromptVersion`'s content-vs-registry split follows SYSTEM_ARCHITECTURE.md §5.1's "prompts are versioned configuration artifacts... files under source control" directly — a DB-editable prompt-content table would risk exactly the prompt-injection-through-configuration concern §5.1 already flags. |
| `LlmProviderPort` abstraction; `openai` the only new runtime dependency | One interface (`complete(request): Promise<result>`) covering system prompt + bounded message history + tool definitions in, natural-language content + parsed tool calls out. `OpenAiLlmProvider` is the only file importing the `openai` package. Retry (bounded, `AI_MAX_RETRIES`, exponential backoff, explicit — not the SDK's own retry) and timeout (`AI_REQUEST_TIMEOUT_MS`) are handled entirely inside the adapter; it either returns a real result or throws exactly one exception type, `LlmProviderUnavailableException`. | Directly serves the "LLM providers replaceable through an abstraction" requirement — swapping providers is one new adapter class. Mirrors `WhatsAppCloudApiError`'s "typed error, caller decides what to do" precedent (`whatsapp-cloud-api.client.ts`), the closest prior art for a third-party API adapter in this codebase. |
| Fallback strategy: always resolves, never surfaces a raw error | On `LlmProviderUnavailableException`, `ConversationOrchestratorService` returns the tenant-configurable `fallbackMessage` (or a sensible default) and auto-escalates the conversation (`ActorType.SYSTEM`) — the caller (webhook processor or `/ai/chat`) always gets a `200`/successful result with `meta.degraded: true`, never a `5xx`. A tool-execution failure (e.g. a hallucinated `serviceId`) is caught per-tool-call and fed back to the model as a structured `role: 'tool'` result rather than aborting the turn — the model is instructed (system prompt) to respond gracefully or escalate, never to surface the raw error. | SYSTEM_ARCHITECTURE.md §5.10 exactly. Verified live against a real (intentionally invalid) `OPENAI_API_KEY` in local dev: the "Test my AI" sandbox correctly rendered the fallback message with a visible degraded indicator, and the conversation escalated in the database — the whole failure path exercised end to end, not just unit-tested. |
| Repeated-clarification-loop detection, not a true confidence score | `AIContext.state` tracks `lastAiReply`/`repeatedReplyCount`; an exact-repeat AI reply past a tenant-configurable threshold (`general.ai.confidenceThreshold`, default 2) triggers auto-escalation (`ActorType.AI`). | SYSTEM_ARCHITECTURE.md §5.10 calls for escalating "the same clarifying question loops," but OpenAI's Chat Completions API returns no usable per-turn confidence score to threshold against. This is the concrete, testable proxy actually available — documented here as a deliberate, narrower implementation of that requirement, not a silent gap. |
| No new BullMQ queue; AI turns run inside the existing `whatsapp-inbound` job | The orchestrator call happens synchronously within `InboundMessageProcessorService.processInboundMessage`, bounded by the LLM provider's own timeout. A failure is caught locally and never rethrown to the outer job handler — a `Message` row is already correctly persisted by that point, and letting an AI failure fail the whole BullMQ job would retry message ingestion (which the idempotency check would then just skip) without ever re-attempting the AI response, silently orphaning the customer's message. | Simpler than a second queue hop for a synchronous LLM call; the fallback strategy above already gives every turn a bounded worst case. A dedicated `AiRateLimitGuard` (Redis `INCR`+`EXPIRE`, `ratelimit:ai:{tenantId}:{periodBucket}`) implements API_SPECIFICATION.md's already-documented "AI-Conversational" per-tenant rate tier (30 req/min) on `POST /ai/chat` — the one new piece of infra this milestone adds, directly serving the "Cost Predictability" NFR. |
| `PATCH /conversations/:id/assign` — new endpoint | A dedicated "take over"/"unassign" action endpoint (STAFF-broad, `TenantActiveGuard`), delegating to the already-existing `ConversationsService.assignUser` (built in Milestone 7 but never exposed over HTTP). | The frontend's "Human takeover controls" requirement needed a real HTTP surface that didn't exist yet — a small, necessary gap-fill discovered during this milestone, not a design change to Milestone 7's own scope. |
| No plan-based usage limiting (`PLAN_MESSAGE_LIMIT_EXCEEDED`) | Not built. | Depends on `Subscription`, which doesn't exist until Milestone 9 (Billing) — explicitly out of scope per this milestone's own brief. |

## Consequences

- `openai` is now a standing dependency. No `axios`/`@nestjs/axios` needed — the SDK's own fetch-based client is used directly, consistent with `WhatsAppCloudApiClient`'s existing precedent of using bare `fetch`.
- `nest-cli.json` gained an `assets` entry copying `modules/ai/prompts/**/*.md` into `dist/` on build — the first static (non-`.ts`) runtime asset this codebase has needed. This surfaced a **pre-existing, unrelated bug**: `tsconfig.build.json` had no `rootDir`, so `nest build`/`nest start` emitted to `dist/src/...` while `package.json`'s `start:prod` (`node dist/main`) and the asset copier both expected `dist/...` directly — `start:prod` was silently broken before this milestone touched it. Fixed by adding `"rootDir": "./src"` (and excluding `prisma/`) to `tsconfig.build.json` only — the shared root `tsconfig.json` (used by `tsc --noEmit`, Jest, the IDE) is untouched.
- `AppointmentsService`/`ConversationsService`/`MessagesService` are each measurably larger now (new sibling methods) but every pre-existing method, test, and HTTP call site is byte-for-byte unchanged in behavior — confirmed by the full pre-existing test suite passing unmodified alongside the new `*ForAi`/`escalateConversation`/`sendAiMessage` coverage.
- `AppointmentsModule` and `SalonModule` now export `AppointmentsService` and `SalonProfileService` respectively (neither was exported before — a pre-existing gap this milestone needed to close, since no prior consumer needed them from outside their own module).
- `frontend/src/app/shared/constants/role-permissions.constant.ts` gained `ai:manage` for `OWNER`/`MANAGER`/`SUPER_ADMIN`, mirroring `backend/prisma/seed.ts` exactly, per that file's own documented maintenance-cost convention.
- Live-verified in a real browser against a real running backend (fake `OPENAI_API_KEY`, so the actual completion call fails): the "Test my AI" sandbox round-trips through `POST /ai/chat` → `ConversationOrchestratorService` → `OpenAiLlmProvider` → `LlmProviderUnavailableException` → the tenant's configured fallback message, rendered with a visible "degraded" indicator in the UI. This is the one path hardest to trust from unit tests alone, and it worked exactly as designed on the first live run.
